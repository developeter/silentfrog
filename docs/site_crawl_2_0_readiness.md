# Site Crawl — 2.0.0 readiness audit

> Written 2026-09-11 against `feature/v2.0` `c63dd58` (the 2.0.0 release candidate) by an eight-lens audit
> (runtime smoke, engine safety, store/history, threading/lifetime, exports, recap/table, docs-vs-code, CLI parity).
> Every finding was independently re-reproduced by a skeptic before being fixed; every fix carries a regression
> test proven to fail without it. The fixes are committed on top of `c63dd58`.

## Verdict

**Ready for 2.0.0, with the fixes below applied.** The end-to-end runtime smoke
(real local site, real threaded crawl, every result-action button, stop mid-run,
close mid-run, CLI/GUI row parity) passed with no traceback; all 20 confirmed
release-blocking findings are fixed with regression tests; the full doctor
(7 gates, ~1,700 tests, diff-cover) is green on the final tree.

Two things this audit could not do and a human should before tagging:

- run a real crawl against a real site (the audit only used local fixture
  servers, by design — no public traffic);
- glance at the eight "real, not fixed now" items below and decide whether any
  should block the tag. None crashes, loses data or misleads a user; the
  largest is `render_js` launching a browser per page instead of using the
  shared `RenderPool` (opt-in feature, slow rather than wrong).

Deliberately left alone: the `WA_DeleteOnClose` one-liner that would reclaim
closed Site Crawl windows. It would make the window really be destroyed on
close while a crawl thread may still be running — the exact crash class the
R1/R3/R4 lifetime work removed — so it needs the `closeEvent` detach first and
is not a release-time change.
